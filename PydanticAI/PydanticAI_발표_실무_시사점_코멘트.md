## 1. 작은 데모의 관찰 대상을 답변에서 상태 전이로 넓히기

**발표 핵심:** PydanticAI의 특징은 결과 문장과 함께 다음 Node가 선택된 이유를 보여 줄 때 드러난다.

**연결할 원문:** 4.1 가장 중요한 내부 Node — 원문 166행, [교재의 추가 코멘트](html/deep/unit-03.html#seminar-pydanticai-node-demo)

가상의 웨이퍼 온도 조회를 “질문 → 모델의 Tool 요청 → 조회 결과 → 유효 Output”으로 구성하고 각 단계를 원문의 Node와 나란히 제시할 수 있다. 그러면 사용법 데모가 끝난 뒤 어떤 제어 구조를 제공하는지 설명으로 이어갈 수 있다. 여기서 보여 주는 것은 관찰 가능한 요청·결과·전이이며 모델의 숨겨진 추론 기록이 아니다.

같은 작은 과제에서 Tool 없이 답한 경우, 조회 인자가 잘못된 경우, 유효 Output을 받은 경우를 구분하면 상태기계를 배워야 하는 이유가 분명해진다. 이 구성은 2차의 데모 제안이며, 실제로 이 경로가 재현되었다는 보고가 아니다.

**3차 확인 질문:** 모델을 사용하는 실행과 고정된 모의 응답을 쓰는 실행에서, 무엇을 재현할 수 있고 무엇은 달라질 수 있는가?

**기술 근거:** [원문의 해당 절](html/deep/unit-03.html#line-166) · [원문 출처 1](https://github.com/pydantic/pydantic-ai/blob/v2.61.0/pydantic_ai_slim/pydantic_ai/_agent_graph.py)

## 2. 병렬 조회의 기준을 속도보다 데이터 의존성으로 정하기

**발표 핵심:** 동시에 호출할 수 있다는 것과 같은 분석 근거로 합칠 수 있다는 것은 다르다.

**연결할 원문:** 11.2 실제 Barrier 분할 코드의 의미 — 원문 539행, [교재의 추가 코멘트](html/deep/unit-06.html#seminar-pydanticai-barrier-data-contract)

가상의 온도·압력 조회가 같은 Lot와 동일한 데이터 스냅샷을 독립적으로 읽는다면 병렬 구간 후보가 된다. 압력 조회 조건이 온도 결과에 따라 달라진다면 선행 조회를 마친 뒤 조건을 정해야 한다. 원문의 Barrier를 이런 데이터 의존성과 연결하면 단순 “async가 빠르다” 설명을 넘어설 수 있다.

병렬화의 이점은 독립 조회의 대기를 겹칠 여지에 있다. 다만 조회 시점에 따라 변하는 데이터를 섞으면 실행 속도와 별개로 분석 근거가 어긋날 수 있다. 따라서 예시의 독립성에는 함수끼리의 호출 관계뿐 아니라 분석 대상·시점·자료 버전 계약도 포함한다. sequential 설정이 이 업무 계약을 대신 만들어 주지는 않는다.

**3차 확인 질문:** 완료 순서를 바꾸거나 한 조회의 스냅샷 버전을 바꿔도, 후속 계산이 잘못된 조합을 식별하는가?

**기술 근거:** [원문의 해당 절](html/deep/unit-06.html#line-539) · [원문 출처 1](https://github.com/pydantic/pydantic-ai/blob/v2.61.0/pydantic_ai_slim/pydantic_ai/_tool_execution.py)

## 3. EndStrategy를 답변 형식이 아닌 실행 정책으로 설명하기

**발표 핵심:** 같은 모델 응답이라도 최종화 정책에 따라 실행되는 Tool의 범위가 달라질 수 있다.

**연결할 원문:** 12.4 실제 판단 사고 실험 — 원문 662행, [교재의 추가 코멘트](html/deep/unit-07.html#seminar-pydanticai-endstrategy-effects)

가상의 응답에 “계산 근거 조회 → 최종 분석 제출 → 외부 배포 요청”이 함께 있다고 두고, 원문의 early·graceful·exhaustive 조건을 대조할 수 있다. 비교 대상은 답변 문체가 아니라, 유효한 Output 발견 전후에 어떤 작업을 실행·건너뛰는지다. 실제 배포 대신 호출 여부만 기록하는 대체 Tool을 쓰는 데모 구상으로 범위를 제한한다.

이 관점은 “분석 결과 생성”과 “보고서 배포”를 같은 Run 안에 둘지 판단하는 데도 쓸 수 있다. 배포를 별도 업무 단계로 분리하면 최종화와 부작용의 관계를 설명하기 쉬워지지만, 두 단계를 잇는 결과·승인 계약이 추가된다. 유효하지 않은 Output, ModelRetry, 이미 확정된 Streaming Output의 예외는 원문 조건을 그대로 적용해 읽어야 한다.

**3차 확인 질문:** 동일한 모의 모델 응답에서 세 정책별 Tool 호출 기록은 어떻게 다른가? Output 검증 실패를 넣으면 그 차이가 유지되는가?

**기술 근거:** [원문의 해당 절](html/deep/unit-07.html#line-662) · [원문 출처 1](https://github.com/pydantic/pydantic-ai/blob/v2.61.0/pydantic_ai_slim/pydantic_ai/_agent_graph.py) · [원문 출처 2](https://github.com/pydantic/pydantic-ai/blob/v2.61.0/pydantic_ai_slim/pydantic_ai/_tool_execution.py)

## 4. 승인 대기를 처리 시간보다 결정 주체로 구분하기

**발표 핵심:** 코드가 즉시 판정할 조건과 사람이 검토해야 할 판단을 같은 대기로 만들 필요는 없다.

**연결할 원문:** 16.3 Inline 해결과 Stop-the-world를 구분 — 원문 888행, [교재의 추가 코멘트](html/deep/unit-09.html#seminar-pydanticai-deferred-review)

가상의 공정 보고서에서 허용 기간·필수 필드 확인은 코드로 판단할 조건이고, 원인 가설을 채택할지는 담당 엔지니어가 근거를 보고 판단할 수 있다. Inline과 후속 Run의 Deferred 해결을 비교할 때, 단순한 대기 길이보다 누가 어떤 자료를 보고 결정하는지를 기준으로 삼을 수 있다.

후속 Run으로 판단을 넘기는 방식은 현재 실행과 사람의 검토 수명을 분리하는 데 활용할 여지가 있다. 그 대신 검토한 보고서 버전·대기 Call ID·반환 결과를 함께 연결해야 한다. 보고서가 수정됐는데 이전 초안의 승인이 재사용되는 상황도 별도 확인 대상이다. 2차에는 이 계약을 제시하고 저장·인증·장애 복구의 실제 구현은 3차 검증으로 남긴다.

**3차 확인 질문:** 보고서 초안이 바뀐 뒤 이전 초안의 승인 응답을 보내면 어떤 상태로 처리해야 하는가?
