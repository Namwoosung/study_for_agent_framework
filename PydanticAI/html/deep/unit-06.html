11. Tool 병렬 실행, 장벽, 순서와 취소#

11.1 '모델이 여러 Tool을 요청'과 '실제 병렬 실행'은 별개#

모델 응답에 두 개 이상의 ToolCallPart가 포함될 수 있다. 그러나 Runtime이 다음을 결정한다.

  • 동시에 시작해도 되는지
  • 어디서 순차 실행해야 하는지
  • 결과를 어떤 순서로 기록할지
  • 실패가 나면 나머지 Task를 어떻게 처리할지

[DOC] PydanticAI는 기본적으로 asyncio.create_task로 여러 Tool 실행을 동시에 스케줄하며, sequential=True가 있으면 앞뒤 실행을 분리하는 장벽(Barrier) 으로 사용한다. 동기 함수는 Worker Thread로 오프로딩할 수 있다. Advanced Tool Features.

11.2 실제 Barrier 분할 코드의 의미#

[SRC] _tool_execution.py의 _segment_by_barriers가 순서를 유지하면서 다음과 같은 세그먼트를 만든다.

원문 흐름·데이터 예시text
Model emitted:
  A(read), B(read), C(write: sequential), D(read), E(read), F(sequential)

Execution segments:
  [A, B] → [C] → [D, E] → [F]

[A,B] concurrent
[C] alone
[D,E] concurrent
[F] alone

장벽은 단순한 Lock과 다르다. Lock은 공유 자원의 동시 접근만 제어하지만, 여기서는 요청 순서 자체를 일련의 실행 구간으로 분할한다.

학습용 의사코드·구조 예시 · 본문에서 실제 코드 여부 확인python
# [PSEUDO] Barrier partition 논리의 축약
segments = []
current_parallel = []
for call in model_emission_order:
    if call.sequential:
        if current_parallel:
            segments.append(current_parallel)
            current_parallel = []
        segments.append([call])
    else:
        current_parallel.append(call)
if current_parallel:
    segments.append(current_parallel)

실제 함수·입력·출력은 소스 _segment_by_barriers에서 확인 가능하다.

11.3 실행 순서와 결과 순서#

병렬 Task는 스케줄한 순서대로 완료되지 않는다. A가 먼저 요청됐어도 B가 먼저 끝날 수 있다. 따라서 다음을 구분해야 한다.

  1. Emission order: 모델이 Tool Call을 생성한 순서.
  2. Start order: Runtime이 Task를 만든 순서.
  3. Completion order: 네트워크·디스크 등 실제 작업 완료 순서.
  4. History assembly order: Tool 결과를 모델 히스토리에 넣는 순서.

[SRC] v2.61.0 _tool_execution.py의 ToolAvailabilityDelta 중복 제거 코멘트는 완료 시점의 경쟁에 의존하지 않고 모델 호출의 인덱스 순서로 선택해야 결정적 결과를 얻는다고 명시한다. 이는 병렬성에서 '실행은 병렬, 기록은 결정적' 패턴의 예시다.

11.4 async와 Thread가 같은 것은 아니다#

  • 비동기 I/O Tool: 이벤트 루프에서 기다리는 동안 다른 Task가 진행.
  • 동기 Tool: 별도 Thread에서 실행돼 다른 Task를 방해하지 않게 할 수 있음.
  • CPU 집중 Tool: Python Thread가 CPU 작업의 실질적인 병렬 속도 향상을 항상 보장하지 않음. 별도 Process/외부 Worker가 필요할 수 있음.
  • 외부 REST Tool: 요청이 취소되어도 원격 서버에서 이미 수행했을 가능성이 있음.

[DOC] 동기 Tool에 있는 contextvars의 쓰기 변경이 밖으로 전달되지 않는 제약에 주의해야 한다. Advanced Tool Features.

11.5 취소의 진짜 의미#

취소에는 최소 세 단계가 있다.

  1. Python Task 취소 신호 수신.
  2. 로컬 Tool/HTTP Client가 취소를 처리.
  3. 원격 시스템이 실제 비즈니스 작업을 중단.

보장 범위는 1→3으로 자동 전파되지 않는다. 따라서 중요한 작업에는 Timeout, Idempotency Key, 중복 요청 탐지, 작업 상태 조회, 보상 트랜잭션이 필요하다.

11.6 도구를 모두 sequential=True로 만들면 안전할까?#

아니다. 동시 실행이 사라질 뿐 다음 문제는 여전히 남는다.

  • 두 Run이 동일한 Tool을 동시에 호출할 수 있음.
  • 외부 DB가 트랜잭션 격리를 보장하지 않을 수 있음.
  • 재시도로 이미 처리한 작업이 중복 수행될 수 있음.
  • Tool 함수 자체가 잘못된 권한 범위를 사용할 수 있음.

설계 결론: 병렬 제어는 한 Run의 Call Batch 경계에서 작동하는 부분과 전체 시스템의 리소스 동기화를 분리해야 한다.
