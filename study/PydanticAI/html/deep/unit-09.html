16. Human-in-the-loop·Deferred Tool·복원#

16.1 Deferred를 정확히 이해하자#

PydanticAI의 Deferred Tool은 다음 두 경우를 처리한다.

  • 승인 필요: 특정 모델 ToolCall을 사람이 검토해야 한다.
  • 외부 실행: 결과가 나중에 도착하거나 별도 Worker/Frontend가 실행한다.

이는 단순히 await로 오래 기다리는 것이 아니라, 필요하면 현재 Run을 끝내고 외부 결과를 수집한 후 후속 Run으로 이어가는 프로토콜이다.

16.3 Inline 해결과 Stop-the-world를 구분#

방식 실행 방식 적합한 상황
Inline HandleDeferredToolCalls 같은 Run 안에서 Handler가 승인/외부 결과를 즉시 제공 프로그램 내 정책 판정, 빠른 외부 결과
Return DeferredToolRequests Run 종료 후 Caller가 보관·승인·재시작 사람의 응답을 몇 분/며칠 기다림, 다른 Worker 실행

두 방식은 조합 가능하다. 일부 요청은 Inline으로 처리하고, 나머지만 외부로 넘길 수 있다. 이는 복잡한 업무 환경에서 유용한 구조다.

16.4 재개 시 무엇을 보존해야 하는가?#

단순하게 Prompt만 재전송하면 승인 대기 상태가 복원되지 않는다. 공식 문서는 Conversation에 Deferred Request의 상태·메타데이터를 함께 보존하도록 설명한다.

  • 기존 메시지 히스토리
  • 미해결 ToolCall ID
  • 승인 요청인지 외부 호출인지 구분
  • Deferred Tool 요청과 Metadata
  • 후속 결과 매핑
  • conversation_id (연속되는 대화를 식별)
  • 새로운 run_id (후속 실행은 별개의 Run)

이 구분이 없는 시스템은 재시작 시 원래 Tool의 인자·승인 내역을 잘못 엮을 위험이 있다.

16.5 중요한 보안 문서 경고#

[DOC] 공식 Deferred Tools 문서는 클라이언트 제출 승인 정보만으로 Authorization을 보장하지 않는다고 명시한다. 예컨대 클라이언트가 이미 승인한 것처럼 조작한 Message History를 보낼 수 있다면 Approval 기능만으로 민감 작업을 지키지 못한다.

따라서 서버가 다음을 소유해야 한다.

  1. 인증된 사용자/테넌트 식별.
  2. 승인 요청 원본 및 Call ID의 서버 저장.
  3. 승인된 주체·범위·시간·대상 검증.
  4. Tool 내부 재검증.
  5. 감사 로그와 재시도·중복 방지.

이 경계는 PydanticAI의 한계인 동시에, 모든 Agent Framework에 공통으로 필요한 애플리케이션 보안 원칙이다.

16.6 Python 프로세스가 죽으면 알아서 복구되나?#

Deferred Tool/Conversation 구조와 내구성 있는 Workflow 엔진은 다른 층위다.

  • Conversation을 외부 DB에 저장하지 않았다면 재시작 후 복원할 데이터가 사라질 수 있다.
  • Task Queue나 Durable Execution Backend가 없으면 진행 중 Background Job을 추적할 수 없다.
  • PydanticAI 생태계는 Temporal, DBOS 등 Durable Execution 연동을 제공하지만, 설치 자체가 자동적인 영속 복구를 의미하지 않는다.

공식 참고: Persistence, Durable Execution.

발표·실무 시사점 / 추가 해석 · 가상 사례

승인 대기를 처리 시간보다 결정 주체로 구분하기

코드가 즉시 판정할 조건과 사람이 검토해야 할 판단을 같은 대기로 만들 필요는 없다.

가상의 공정 보고서에서 허용 기간·필수 필드 확인은 코드로 판단할 조건이고, 원인 가설을 채택할지는 담당 엔지니어가 근거를 보고 판단할 수 있다. Inline과 후속 Run의 Deferred 해결을 비교할 때, 단순한 대기 길이보다 누가 어떤 자료를 보고 결정하는지를 기준으로 삼을 수 있다.

후속 Run으로 판단을 넘기는 방식은 현재 실행과 사람의 검토 수명을 분리하는 데 활용할 여지가 있다. 그 대신 검토한 보고서 버전·대기 Call ID·반환 결과를 함께 연결해야 한다. 보고서가 수정됐는데 이전 초안의 승인이 재사용되는 상황도 별도 확인 대상이다. 2차에는 이 계약을 제시하고 저장·인증·장애 복구의 실제 구현은 3차 검증으로 남긴다.

3차 확인 질문보고서 초안이 바뀐 뒤 이전 초안의 승인 응답을 보내면 어떤 상태로 처리해야 하는가?
