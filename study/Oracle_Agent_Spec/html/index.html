1. 무엇을 해결하나 #

재고 상담 에이전트를 두 팀이 운영한다고 하자. 한 팀은 WayFlow를 쓰고 다른 팀은 LangGraph를 쓴다. 두 팀 모두 모델 설정, 재고 도구 이름과 입출력, 상담 지침을 공유하고 싶다. Oracle의 Open Agent Specification(Agent Spec)은 이런 구성을 선언하고 JSON이나 YAML로 교환할 수 있게 정의하는 공개 명세다. 명세의 Agent는 에이전트 선언이며, 실행 엔진은 어댑터가 그 선언을 번역한 뒤 동작한다.

구성 담당하는 일
Agent Spec 모델·도구·에이전트·워크플로를 표현하는 구성 형식과 의미를 정의한다.
PyAgentSpec Python 객체로 구성을 만들고 JSON/YAML로 직렬화하거나 역직렬화한다.
런타임 어댑터 구성 요소를 대상 프레임워크의 실행 객체로 변환한다.
WayFlow Oracle의 참조 런타임이다. 에이전트나 플로를 로드해 실행한다.
업무 코드 도구 구현, 인증, 권한, 데이터 저장, 외부 부작용을 처리한다.

Agent에서는 모델이 다음 도구나 응답을 선택한다. Flow에서는 개발자가 실행 경로와 데이터 연결을 명시한다. 둘 다 동일한 명세 생태계에 속한다. MCP는 도구나 리소스를 제공하는 서버와 연결하는 프로토콜이고, A2A는 에이전트 간 요청·응답에 쓰는 프로토콜이다. Agent Spec은 이러한 연결을 포함해 에이전트와 플로의 구성을 기술한다. 언어 명세 · 기술 보고서

2. 기초 — 재고 에이전트를 JSON과 YAML로 내보내기 #

각 Python 블록을 표시된 파일명으로 같은 실습 폴더에 저장한다. 먼저 Python 3.11의 독립 가상환경을 만든다. 이 단계는 모델 API 키를 사용하지 않는다.

내보낸 파일에서 component_type, agentspec_version, 모델 ID, 도구 이름, sku·stock 스키마를 찾는다. 생성된 표현에서 컴포넌트 ID와 참조가 같은 객체를 가리키는 방식도 살펴본다. 도구의 Python 구현은 런타임 레지스트리에 제공한다. JSON에서 같은 도구 이름을 썼더라도 다른 구현을 등록하면 결과가 바뀔 수 있으므로 운영에서는 도구 계약과 구현 버전도 관리한다. PyAgentSpec 저장소 및 시작 예제

3. 중급 — WayFlow에서 선언에 실제 도구 연결하기 #

실제 모델을 호출하려면 OPENAI_API_KEY를 환경 변수에 설정하고, STUDY_MODEL은 계정에서 도구 호출이 가능한 모델 ID로 설정한다. 모델을 바꿨다면 2절의 JSON을 다시 생성한다. 4절에는 키 없이 실행할 수 있는 플로가 있다.

같은 이름을 키로 하여 선언과 구현을 연결한다. 실행 결과에서 KB-01의 7개, MS-02의 0개와 도구 요청·응답을 확인한다. 미등록 SKU는 상품 없음으로 별도 처리한다. Agent의 프롬프트는 조회를 요청하도록 유도한다. 조회가 업무상 반드시 필요한 경우 4절처럼 도구 노드를 플로에 둔다. WayFlow에서 실행하기

4. 심화 — 고정 조회 절차를 Flow로 만들기 #

같은 도구를 모델 선택 없이 한 번 실행한다. 제어 엣지는 시작 → 조회 → 종료 순서를, 데이터 엣지는 시작의 sku → 조회의 sku, 조회의 stock → 종료의 stock 연결을 나타낸다. 이 구분 덕분에 실행 순서와 전달되는 값을 따로 읽을 수 있다.

위 순서대로 stock_spec.py, stock_flow.py, run_stock_flow.py를 실행한다. 4절에서는 run_wayflow.py에서 등록할 도구만 재사용한다. Flow에서 조건 분기가 필요하면 분기 노드 또는 FlowBuilder.add_conditional의 매핑과 기본 목적지를 선언한다. 주문 수정이나 취소라면 권한 검사, 승인, 실제 변경을 별도 단계로 분리하고 변경 작업의 멱등성 키를 업무 시스템에 전달한다. 조건 분기 · FlowBuilder

5. 심화 — 같은 Agent Spec을 LangGraph에 로드하기 #

26.3.1 배포판에서 WayFlow Core와 PyAgentSpec의 LangGraph extra가 서로 겹치지 않는 anyio 범위를 요구한다. 런타임별 가상환경을 나누고 같은 JSON을 입력으로 사용한다.

WayFlow Core 26.3.1 배포본에서는 대화 객체의 execute()를 사용한다. LangGraph에서는 변환된 그래프에 메시지 상태를 넘긴다. 이식되는 것은 명세에 표현되고 어댑터가 지원하는 구성이다. 각 런타임의 대화·체크포인트 데이터, 호출 제한과 오류 처리, 프레임워크 전용 미들웨어는 별도로 비교한다. LangGraph 에이전트를 Agent Spec으로 내보내는 어댑터도 있지만 사용자 정의 Python 노드와 상태를 포함한 임의 그래프가 그대로 왕복 변환된다고 가정하면 안 된다. 대상 버전의 지원 항목을 확인하고 실제 구성으로 테스트한다. LangGraph 어댑터 · 어댑터 API

6. 제작 관점의 장단점 #

장점 그에 따르는 작업
선언과 실행 코드를 분리해 구성 변경을 검토하고 배포할 수 있다. 명세·어댑터·런타임·업무 도구의 버전 조합을 관리한다.
도구 입출력과 플로의 연결을 명시할 수 있다. 스키마 검증에 더해 실제 도구의 업무 의미와 권한을 검사한다.
지원되는 구성으로 여러 런타임을 실험할 수 있다. 고유 노드·모델·승인·스트리밍·예외 동작의 지원 여부를 확인한다.
같은 구성으로 후보 런타임을 비교하기 쉽다. 모델 호출 순서, 프롬프트 조립, 상태 복구, 지연과 비용을 별도로 측정한다.

LangChain으로는 도구를 등록해 바로 에이전트 루프를 구성할 수 있고, LangGraph는 실행 상태와 엣지를 애플리케이션 코드에 직접 표현한다. Deep Agents는 계획·작업 공간·위임을 묶은 하네스다. Agent Spec을 쓸 때는 구성 배포와 런타임 교체가 필요한지, 필요한 기능이 이식 가능한 범위 안에 있는지가 판단 기준이다. 한 런타임에서 커스텀 노드를 자주 수정하는 경우에는 어댑터 계층을 유지하는 비용도 계산한다.

7. 운영 점검과 소스 읽기 #

  1. 검증을 두 층으로 나눈다. 직렬화 왕복에서 도구와 데이터 연결이 유지되는지 확인한다. 실행 테스트에서는 값과 분기 외에도 도구 호출 횟수, 인자, 오류, 승인 거절 시 외부 변경 0회를 검증한다.
  2. 신뢰 경계를 지정한다. 제3자 명세를 배포하기 전에 허용 컴포넌트와 도구 목록, 접속 대상 URL, 템플릿과 플러그인을 검토한다. 로더의 허용·차단 옵션과 실행 환경의 네트워크 정책을 함께 적용한다. 원격 호출에는 사용자·테넌트 권한을 사용하고 비밀은 실행 환경에서 주입한다.
  3. 업그레이드 전에 양쪽을 비교한다. 동일 SKU, 미등록 SKU, 잘못된 입력, 도구 예외, 모델 호출 실패를 각 런타임에 넣어 본다. 최종 응답 문구 외에 구조화 결과와 실행 기록을 비교한다.
  4. 실행 코드로 확인한다. 소스의 어댑터 공통 로더에서 역직렬화와 컴포넌트 변환 경계를 찾고, LangGraph 어댑터의 서버 도구 변환과 WayFlow의 로더를 비교한다. 선언에 적힌 이름이 각 런타임의 함수 또는 도구로 연결되는 지점이 핵심이다.
