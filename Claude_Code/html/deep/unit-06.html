Part III. Instructions·Memory·Sessions의 로딩과 우선순위

11. Instruction은 파일을 읽는 것과 정책 강제가 다르다#

CLAUDE.md는 프로젝트 규칙·코딩 스타일·작업 방식 등을 모델 입력에 전달하는 Instruction 텍스트다. 파일 내용이 완벽한 권한 정책으로 변환되는 것은 아니다. Instruction은 모델이 고려하지만, 실제 Tool 실행을 중단하는 것은 Permission·Hook·Sandbox·Tool Backend의 역할이다. DOC[R07]

11.1 파일 위치별 사용 목적#

위치 범위 관리 관점
Organization managed 조직 정책·공통 규칙 배포·관리자 강제와 검토 필요
~/.claude/CLAUDE.md 사용자 공통 여러 프로젝트에 적용되는 선호·규칙
프로젝트 루트 CLAUDE.md 프로젝트 전체 협업 기준, 빌드·테스트·안전 수칙
하위 디렉터리 CLAUDE.md 관련 파일/폴더 탐색 시 작업 컨텍스트와 연관된 세부 규칙
.claude/rules/*.md 세분화된 규칙 경로별 또는 범위 없는 규칙 분리
CLAUDE.local.md 개인 로컬 공유하지 않는 로컬 작업 지침
AGENTS.md Claude 외 다른 도구와 공유 가능 로딩 방식과 CLAUDE.md 공존 정책 확인

이 표는 의미적 범위를 설명한다. 정확한 병합·중복·우선순위 처리는 설정과 버전, 로더 정책에 의존한다.

12. AGENTS.md 지원을 정확히 이해하기 — 2026년 10월#

최신 공식 문서는 AGENTS.md를 전용 내장 Plugin을 통해 지원한다고 설명한다. 기본 설정에서 CLAUDE.md와 AGENTS.md를 무조건 모두 읽는 것은 아니다. DOC

  • 기본 claude-md-or-agents-md: 작업 디렉터리 및 상위 경로에 CLAUDE.md/CLAUDE.local.md가 없으면 AGENTS.md를 읽는 fallback.
  • claude-md-and-agents-md: 두 형식을 함께 읽음. 동일한 AGENTS.md가 import로 이미 들어왔으면 중복을 피함.
  • claude-md: Claude 형식만 읽음.
  • managed-only: 관리형 정책 중심으로 제한하는 특별 구성. 세부 on-demand 예외를 확인해야 함.
  • AGENTS.md 기본 지원은 특정 버전 이후 도입됐고, 과거 버전·일부 활성화 상태에서 지원이 다를 수 있다.

공식 문서가 제공하는 구성 예시는 다음과 같다. [DOC] (설치된 해당 버전에서 기능 사용 가능 여부 확인)

원문 수록 코드 예시 · 실행 미검증json
{
  "pluginConfigs": {
    "cc-plugin-agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}

위 설정은 공식 문서에 따라 사용자 설정 또는 Managed Settings에 두는 방식이며, 프로젝트/로컬 설정에서 같은 값을 적었다고 항상 반영되는 것이 아니다. AGENTS.md 로더는 CLAUDE.md 로딩 시 발생하는 InstructionsLoaded Hook과 동작이 다를 수 있다. DOC

12.1 비교·발표에서 중요한 설계 포인트#

AGENTS.md 지원 여부만 보는 것은 불충분하다. 어떤 파일을 선택하는지, 우선순위, 중복 회피, 대화 압축 뒤 재로드 조건, 외부 경로 import 승인, 하위 폴더 로딩 조건을 확인해야 한다. 파일 이름은 Agent에게 규칙을 읽히는 인터페이스일 뿐이며, 정책의 실행 엔진은 아니다.

13. Path-scoped Rules — 언제 모델에 보이는가?#

루트 규칙을 모두 매번 Prompt에 넣으면 컨텍스트가 낭비된다. 파일 경로와 연관된 규칙은 그 경로에서 파일을 열거나 수정할 때 삽입하는 방식으로 지연 로딩할 수 있다. 하지만 paths로 한정된 규칙은 압축 전 대화에 포함되었다가 요약되는 과정에서 사라질 수 있다. DOC[R05]

원문 수록 코드 예시 · 실행 미검증yaml
---
paths:
  - "src/analysis/**/*.py"
---
# 예시: 수치 분석 작업 규칙
- 결과에 사용한 단위와 집계 기준을 명시한다.
- 원본 데이터를 수정하는 명령은 실행하지 않는다.

분석 포인트: 파일 변경과 Instruction 로딩의 연관을 갖는 event-driven context injection은 비용 면에서 유리하지만, 보안 핵심 정책을 여기만 두면 로딩 이벤트를 놓쳤을 때 정책이 적용되지 않을 수 있다. 보안 강제는 별도 검사 계층에 둔다.

14. Auto Memory는 누가 쓰며 언제 로딩되는가?#

Claude Code의 Auto Memory는 모델이 향후 유용하다고 판단한 정보를 파일로 남기는 기능이다. 공식 문서는 user, feedback, project, reference 유형을 설명하며, 코드·Git 기록이나 CLAUDE.md만으로 다시 알 수 있는 사실은 저장 대상에서 제외하려 한다. 모든 세션에 반드시 기억을 남기는 것은 아니다. DOC

14.1 파일 기반 구조#

원문 흐름·데이터 예시text
~/.claude/projects/<project>/memory/
  MEMORY.md              # 작은 메모리 색인
  user_role.md            # 주제별 파일
  feedback_testing.md
  ...
  • MEMORY.md는 상세 내용을 모두 넣는 파일보다 다른 주제 파일로 이어지는 Index 역할을 한다.
  • 2026-10-31 공식 문서 기준 시작 시 MEMORY.md는 최대 200줄 또는 25KB 중 먼저 걸리는 한도까지 로드된다.
  • 머신 로컬 저장이므로 클라우드·다른 장비·프로젝트 전체에 자동 공유된다고 가정하면 안 된다.
  • 긴 세션 기록의 보존·삭제 정책과 Auto Memory 파일의 보존은 다르다. DOC

14.2 Memory의 업데이트가 즉시 Prompt에 반영되는가?#

파일이 쓰였다는 사실과 이미 모델에 보내진 System/Project Context가 바뀌는 것은 다르다. 기록 변경 내용은 모델이 다시 파일을 읽거나, 지정된 시점에 Context를 다시 구성할 때 들어온다. Claude Code는 Prefix 안정성을 고려하여 프로젝트 지침·메모리를 특정 경계에서 새로 로드할 수 있다. DOC[R05]

14.3 장기 메모리에서 가장 중요한 실패 종류#

  1. 선택 실패: 저장해야 할 중요 맥락을 모델이 기록하지 않음.
  2. 추론 오류: 잘못 이해한 사실을 Memory로 고정.
  3. 시간 경과: 예전의 프로젝트 결정이 현재 상황과 충돌.
  4. 검색 실패: 토픽 파일이 있지만 Index가 갱신되지 않아 찾지 못함.
  5. 공유 경계: 로컬에서 유용했던 메모리가 서버 실행 환경에 존재하지 않음.
  6. 기밀 노출: 자동 저장된 민감 데이터가 예상보다 오래 남음.

설계 교훈: Auto Memory의 편의성과 신뢰성은 다른 축이다. 개발용 자체 Agent에서는 Memory의 provenance, 수정 승인, 삭제 및 TTL, 검색 품질, 갱신 이력을 별도로 설계해야 한다.

15. Session History와 Auto Memory는 다르다#

항목 Session Auto Memory
주된 기능 특정 대화 흐름의 이어가기 대화를 넘어 재사용할 작은 지식
저장 내용 대화 메시지·Tool 호출 결과 등의 기록 선택된 사실·선호·프로젝트 참조
다시 읽는 방식 --resume, --continue 등 세션 시작 시 Index + 필요시 Topic 열람
유실 위험 압축으로 모델 가용 원문 축소 오래된/잘못된 기억 및 인덱싱 실패
상태 일관성 외부 파일 변경과 별도 파일 수정·로딩 시점에 의존
보안 초점 개인/업무 기록 보존 정책 반복 사용되는 민감 내용 축적 관리

재개 ≠ Rollback: --resume는 이전 대화에 이어 입력하는 기능이지, 이전에 수행한 Bash/DB 변경을 원상복구하는 트랜잭션 기능이 아니다. /rewind의 파일 Checkpoint 역시 외부 서비스에 발생한 부작용을 보장된 방식으로 취소하지 못한다. DOC[R09]
