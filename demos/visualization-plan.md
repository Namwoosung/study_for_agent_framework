# 데모 시각화 개선 계획

## 공통 화면

첫 화면은 시나리오별 흐름도, 현재 단계의 대표값, 최종 결과로 구성한다. 흐름도에는 실행 주체와 화살표 방향을 표시하고, 각 화살표에 오간 데이터의 이름과 대표값을 붙인다. 예를 들어 Tool 결과의 “불량률 4.2%”를 누르면 “검사 1,000개 · 불량 42개”와 실제 반환값을 볼 수 있다. 이 숫자는 시나리오 데이터의 예시이며, 실행 화면에는 해당 실행에서 관측한 값을 표시한다.

1. 실행 전에는 예시 입력과 예상 경로를 보여준다. 실행 중에는 이벤트에 맞춰 진행 중·승인 대기·완료·실패를 표시한다. 계획된 경로와 관측된 경로를 구분하고, 선택되지 않은 도구나 수집하지 못한 단계는 각각 구분해 표기한다.
2. 단계나 화살표를 고르면 그 구간의 실제 입력·출력을 나란히 보여준다. 기본 화면에는 값의 의미와 단위, 출처를 표시한다. 전체 JSON, 긴 프롬프트, 스키마 정의, 반복 이벤트, 스택 트레이스는 접어둔다. 발표 중에는 실행 화면을 그대로 두고 이전 라운드를 다시 열 수 있게 한다.
3. 공통 이벤트 목록은 원본 확인용으로 유지한다. 시각화에는 run·부모/자식·모델 요청·tool call·비교 정책 식별자를 사용한다. 현재 이벤트에 없는 연결은 관측 지점에 식별자를 추가하고, 시간순만으로 인과관계를 만들지 않는다. 요청·응답 본문은 기존 실제 호출에서 수집하고, 요약과 분류는 화면에서 파생한다.

## Hermes

| 서브 데모 | 첫 화면과 대표값 | 열어서 확인할 내용 |
| --- | --- | --- |
| Agent Loop | 사용자 → Hermes → 모델 → 도구 → 모델 → 답변. 라운드를 가로로 놓고 어떤 호출 결과로 다음 라운드가 열렸는지 표시 | 관측한 함수 경계, 단계별 입출력, 재시도·예산·오류 분기 |
| Context | 라운드 선택과 이전 모델 요청 대비 변경점. 시스템 지시, 대화 이력, 이번 입력, 모델의 tool call, tool 결과를 역할별로 표시 | 시스템 메시지 안의 구성요소는 출처를 관측할 수 있을 때만 분리. tools·모델 옵션은 messages 바깥의 요청 필드로 구분. 긴 블록과 전체 전송 본문은 접기 |
| Session Search | 모델이 보낸 검색어 → FTS 조회 조건 → 검색된 세션 → tool 반환값 → 다음 모델 요청. 조회 결과와 실제 반영 여부를 연결 | 실제 쿼리, 검색 범위, 후보 및 제외 사유가 수집된 경우 그 근거 |
| Tool Calling | 공개한 스키마 → 모델이 선택한 도구·인자 → 검증 및 hooks → 실행 결과 → 다음 모델 입력. 선택된 도구 한 개를 기본으로 펼침 | 전체 스키마, 다른 공개 도구, hook별 결과, 검증 실패와 오류 처리 |
| 승인 | 명령 → 승인 규칙과 매칭 근거 → 승인 대기 → 사용자 선택 → 실행 결과. 대기 상태에서 결정 버튼을 고정된 위치에 배치 | 매칭된 규칙과 승인 범위, 승인·거절 이후 이벤트. 갱신 중에도 선택 상태 유지 |
| Guardrails | 입력 → 검사 지점 → 허용·차단·승인 필요 → 다음 단계. 판정과 실제 효과를 함께 표시 | 검사에 들어간 값, 적용된 정책과 관측한 근거, 오류 상세 |
| Skills | 생성 또는 수정 의도 → 실제 skill_manage 호출 → 저장 결과. 기존 파일이 있으면 변경 줄부터 표시 | 호출 인자, 변경 전후 파일, 후속 실행에서 실제로 읽힌 경우 해당 경로 |
| 위임 | 부모와 자식별 실행 레인. 작업이 나뉜 지점과 자식 결과가 부모로 돌아오는 지점을 연결 | 자식별 라운드, 호출 및 반환값. 실제로 시간이 겹친 구간만 병렬로 표시 |

## PydanticAI

| 서브 데모 | 첫 화면과 대표값 | 열어서 확인할 내용 |
| --- | --- | --- |
| Agent Graph | 실제 iter() 노드를 실행 순서대로 놓고 각 노드가 받은 값과 다음 노드로 넘긴 값을 한 줄씩 표시 | 이벤트와 메시지 타입, 같은 노드가 반복된 이유 |
| Deps | 애플리케이션에서 주입한 값 → RunContext → 도구에서 읽은 값 → 결과. 모델 전송 여부를 별도 열로 표시 | 허용 bin과 요청 bin, 도구의 검증 분기, 실제 모델 요청 |
| 대화 저장·복원 | 첫 실행 → 저장한 메시지 → 다음 실행이 복원한 이력. 어떤 값이 다음 답변에 쓰였는지 연결 | 저장 형식, 복원 메시지, 두 실행의 실제 요청 차이 |
| 출력 모드 | 네 가지 모드를 같은 입력으로 비교하고, 모델에게 보낸 출력 계약과 실제로 받은 값을 모드별로 표시 | 요청 스키마, 도구 인자 또는 응답 본문, 파싱·검증 결과 및 오류 |
| 종료 정책 | 같은 첫 모델 응답에서 정책별로 분기. 어떤 도구가 실행·생략되었는지와 최종 결과를 비교 | 재사용한 첫 응답과 이후 실제 실행 경로, 관측된 상태 전이 |
| Core | 모델 호출·도구 실행·출력 검증과 앱이 작성한 데이터 접근·저장·정책 코드를 나란히 표시 | 화면 단계별 실제 함수와 연결되는 짧은 코드 |
| Harness | 요청 → Harness 기능 → 상태 반영 흐름. Memory 등 실행 중 실제 사용된 기능과 변경값을 표시 | 기능별 호출 및 저장 이벤트, 연결된 실제 코드 |
| 오케스트레이션 | 상위 Agent → 하위 Agent별 작업·결과 → 상위 Agent 답변. 하위 결과가 어느 단계로 돌아왔는지 표시 | 각 Agent의 요청·응답, 도구 호출 및 실패 전파 |

## 적용 순서와 완료 기준

1. **대표 화면 4개**부터 만든다. Hermes Context·Tool Calling으로 대량 데이터와 양방향 흐름을 검증하고, PydanticAI Agent Graph·종료 정책으로 실행 상태와 비교 레이아웃을 검증한다.
2. **나머지 12개**에 확장한다. 승인과 Guardrails, 검색·저장, 위임, 구성 비교 순으로 적용한다. 현재 공통 이벤트에 없는 값은 실제 프레임워크의 입력·출력 경계에서 수집한다.
3. **실행 검증**을 한다. Hermes의 연속 모델 요청, 승인·거절, tool 실패와 자식 실행, PydanticAI의 대화 복원과 출력 모드·종료 정책 차이를 원본 트레이스와 대조한다. 발표 화면 크기에서 기본 화면만으로 누가 무엇을 받았고 어디까지 진행했는지 읽을 수 있어야 한다. 작은 화면에서는 세로로 배치하고, 키보드로 단계 선택과 상세 펼치기를 지원한다.
